# 04 · Ethereum 为什么出现？

> 本章目标：理解 Ethereum 如何把区块链从“去中心化价值转移系统”推进到“可编程的共享状态机”。读完后，你应该能清楚说明 Account 模型与 UTXO 的区别、Smart Contract 的本质，以及 Gas 为什么是必要的资源计量机制。

Bitcoin 证明了去中心化价值转移可行。但它的设计目标非常聚焦：点对点电子现金。当人们开始想在链上表达更复杂的规则时，新的需求出现了。

---

## 4.1 从“数字货币”到“世界计算机”

Bitcoin 擅长可靠地转移价值，但它的脚本能力有意保持简单和受限。许多更复杂的业务逻辑很难、甚至无法在原生 Bitcoin 脚本中直接实现。

设想一个更复杂的规则：

> Alice 和 Bob 各存入 10 个单位。如果某个外部条件成立，资金转给 Alice；否则退还双方。整个过程不依赖任何中心托管方。

这已经不只是简单转账，而是一个**有条件执行的程序**。

如果区块链要成为一个通用应用平台，就需要一种更通用的执行环境：开发者能够定义任意（在资源限制内的）业务逻辑，网络中的节点能够按相同规则验证执行结果。

Ethereum 的核心主张可以概括为：

> **区块链不仅保存数据，还可以按照协议执行开发者定义的程序，并把执行结果写入共享状态。**

这就是从“数字货币”走向“世界计算机”的范式转移。

---

## 4.2 Smart Contract：把规则变成程序

**Smart Contract（智能合约）**是部署在区块链上、由网络按协议规则执行的程序。

它不是运行在某家公司服务器上的普通 API，而是：

- 代码与状态都记录在链上
- 执行过程受协议约束
- 状态变更必须被网络验证并达成共识后才会被接受

一个简化的执行路径是：

```text
User
  ↓
Transaction（调用某个合约的某个函数，并附带参数与费用）
  ↓
Ethereum Runtime（按协议执行）
  ↓
Smart Contract 代码
  ↓
State Change（账户余额、合约存储等被修改）
```

智能合约让开发者可以把“规则”写成代码，而不是依赖中心化中介来解释和执行规则。

---

## 4.3 Blockchain 变成共享状态机

可以把 Ethereum 理解为一个不断演进的共享状态机：

```text
State₀
  │
  │ Transaction
  ▼
Program Execution
  │
  ▼
State₁
```

下一笔交易继续作用在新状态上：

```text
State₁
  ↓
Transaction
  ↓
Execution
  ↓
State₂
```

整个网络最终维护的是一条所有人都可以验证的、不断变化的共享状态历史。

这和 Web2 后端非常像：

```text
Request
  → Business Logic
  → Database Mutation
```

但关键区别在于信任边界：

- Web2 的执行结果通常只相信一家公司的服务器与数据库。
- 区块链的执行结果必须能被网络中的其他节点独立验证，并最终被共识接受。

因此，Ethereum 把区块链从“主要记录价值转移的账本”推进到了“可以运行通用程序的共享状态机”。

---

## 4.4 Account 模型

Ethereum 采用 **Account 模型**，而不是 Bitcoin 的 UTXO 模型。

最简单的余额例子：

```text
Alice = 10 ETH
Bob   = 5 ETH

Alice → Bob : 2 ETH

Alice = 8 ETH
Bob   = 7 ETH
```

这里的账户是持续存在的状态实体。交易直接修改相关账户的状态，而不需要“消费旧输出、创建新输出”。

与 Bitcoin 的对比：

| 维度 | Bitcoin (UTXO) | Ethereum (Account) |
|------|----------------|--------------------|
| 状态基本单元 | 未花费的交易输出 | 账户（余额 + 可选代码 + 存储） |
| 交易如何表达变更 | 消费旧 UTXO，创建新 UTXO | 直接修改账户相关状态 |
| 找零 | 需要显式的 Change Output | 不需要，余额直接增减 |
| 价值表现 | 可花费的输出 | 账户余额（以及更复杂的合约状态） |
| 复杂逻辑 | 脚本能力有限 | 通过 Smart Contract 表达通用逻辑 |

这不是简单的“哪一个更先进”，而是两种不同的状态建模方式，各有工程取舍。

Ethereum 中常见两类账户：

- **外部账户（EOA，Externally Owned Account）**：由私钥控制，没有代码，主要用于发起交易和持有资产。
- **合约账户（Contract Account）**：由代码控制，有自己的存储，可以被交易调用。

合约账户的存在，让“程序”本身成为链上状态的一部分。

---

## 4.5 Gas：计量与防止滥用

一旦区块链可以执行任意程序，一个新的攻击面立即出现：

```text
while (true) {
    doSomething()
}
```

如果程序可以无限消耗节点的 CPU、内存或存储，却不用承担任何成本，攻击者就能用极低成本拖垮网络。

因此，系统必须对计算与资源消耗进行**计量**，并让发起方为此付费。

**Gas** 可以先理解成：

> 执行区块链程序时，对计算、存储等资源消耗进行计量的单位。

一个简化的费用关系是：

```text
Fee ≈ Gas Used × Gas Price
```

需要区分两个概念：

- **Gas**：资源计量单位（“消耗了多少计算/存储”）
- **Fee**：用户为这些资源支付的经济成本（通常用原生代币支付）

Gas 机制的核心作用是：

1. 防止无限循环与资源耗尽攻击
2. 让资源消耗有明确的经济成本
3. 为区块容量与网络负载提供调节手段

它是可编程区块链几乎不可避免的设计组件。

---

## 4.6 Ethereum 带来的新能力与新问题

### 新能力

有了 Account 模型、Smart Contract 和 Gas，开发者可以在链上构建远比简单转账复杂的应用：

- 去中心化交易所（DEX）
- 借贷与稳定币协议
- NFT 与数字所有权
- DAO 与治理机制
- 各种金融与非金融逻辑的组合

区块链第一次真正具备了“可编程共享状态”的能力。

### 新问题

能力扩展的同时，新的工程压力也随之而来：

- **串行执行倾向**：许多实现中，交易按顺序执行，难以充分利用现代多核硬件。
- **状态膨胀**：合约存储持续增长，节点负担加重。
- **Gas 战争**：网络拥堵时，用户为优先打包支付高昂费用。
- **扩展性瓶颈**：全球共享的单一状态机，吞吐与延迟面临天然限制。
- **验证成本**：复杂程序的执行结果需要被广泛验证，进一步消耗资源。

这些问题把讨论从“如何安全转账”推进到了“如何运行一个全球共享的计算系统，并尽可能高效”。

---

## 4.7 从 Ethereum 到 Solana 的关键问题

到这里，我们可以提出一个非常关键的问题：

> 如果区块链本质上是一个共享状态机，而现代服务器本身拥有大量 CPU 核心、大内存和高速网络，那么为什么不更充分地利用这些并行硬件能力？

答案并不简单。并行执行不是“多开几个线程”就能解决的。

关键在于**状态依赖**：

```text
Tx A 修改 Alice
Tx B 修改 Bob
→ 两者可能互不影响，适合并行
```

```text
Tx A 修改 Alice + Bob
Tx B 修改 Bob + Charlie
→ 共同访问 Bob，存在潜在依赖，不能随意并行
```

如果运行时在执行前无法知道交易会访问哪些状态，就很难安全地做依赖分析与并行调度。

于是下一代系统设计必须认真回答：

> **如何让交易显式声明自己要访问的状态，从而让运行时能够识别依赖并尽可能并行执行？**

这就把我们带到了 Solana。

## 本章小结

1. Bitcoin 解决了去中心化价值转移，但可编程能力有限；更复杂的业务规则需要更通用的执行环境。
2. Ethereum 的核心主张是：区块链不仅可以保存数据，还可以执行开发者定义的程序，并把结果写入共享状态。
3. Smart Contract 是按协议规则在链上执行的程序，状态变更必须被网络验证。
4. Account 模型把状态基本单元从 UTXO 转向持续存在的账户（余额 + 可选代码 + 存储）。
5. Gas 是对计算与资源消耗的计量单位，用于防止滥用并让资源使用有经济成本。
6. Ethereum 开启了可编程共享状态的时代，同时也暴露了串行执行、状态膨胀、费用波动与扩展性等新问题。
7. 这些问题直接引出了 Solana 要重新思考的核心：如何显式管理状态访问，并在安全前提下实现高效并行执行。
