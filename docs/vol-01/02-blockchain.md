# 02 · 区块链如何共同记账？

> 本章目标：把“去中心化账本”拆成可理解的工程问题。读完后，你应该能清楚说明数字签名解决什么、双重花费为什么危险、Transaction 和 Block 各自扮演什么角色，以及 Consensus 真正要回答的是什么。

上一章我们得出结论：钱的问题最终会落到账本问题，而账本的核心困难在于——如果没有中央维护者，一群互不完全信任的参与者如何共同维护一份可信状态？

这一章逐个拆开四个关键问题：

1. 谁有权修改状态？（授权）
2. 同一份价值能不能被花两次？（双重花费）
3. 状态变更请求如何被表达与验证？（Transaction）
4. 网络最终如何形成共同历史？（Block + Consensus）

---

## 2.1 第一个问题：谁有权修改状态？

假设 Alice 的账户里有 100 个单位。网络突然收到一条消息：

```text
Alice → Bob：30
```

节点不能只相信消息里写着“Alice”。任何人都可以伪造一段文字：

```text
“Alice 同意把 30 给 Bob。”
```

如果系统没有可靠的授权机制，任何人都能随意修改别人的余额，账本立刻失去意义。

因此，去中心化账本必须先回答：

> **如何证明“这笔操作确实得到资产控制者的授权”？**

这就是数字签名要解决的问题。

---

## 2.2 数字签名：证明授权关系

数字签名建立了一种公开可验证的授权关系：

```text
Private Key（私钥，仅控制者持有）
     │
     │ sign(message)
     ▼
  Signature（签名）
     │
     │ verify(public_key, message, signature)
     ▼
Valid / Invalid
```

- **私钥**：用于签名，必须保密。
- **公钥**：用于验证签名，可以公开。
- **签名**：证明“控制对应私钥的人确实授权了这段消息”。

从工程视角看，这非常优雅：验证者不需要知道私钥，也不需要相信任何中心机构，只需要用公开的公钥检查签名是否有效。

但这里有一个极其重要的概念边界，后续学习中会反复遇到：

> **签名有效 ≠ 交易一定有效。**

签名只回答一个问题：

> “控制对应私钥的人是否授权了这段消息？”

它**不能**回答：

- 余额是否足够？
- 账户是否被冻结或存在其他限制？
- 是否违反程序 / 合约规则？
- 是否发生了双重花费？
- 是否满足业务条件？

这些问题属于 **Validation（验证）** 和 **Execution（执行）** 层，必须由协议规则和运行时单独检查。

把“授权”和“合法性”混为一谈，是理解区块链时最常见的错误之一。

---

## 2.3 第二个问题：双重花费（Double Spending）

数字数据可以被轻易复制。这给去中心化账本带来了传统纸币或实物货币没有的新问题。

假设 Alice 只有 10 个单位，她同时广播两笔交易：

```text
Tx A：Alice → Bob      10
Tx B：Alice → Charlie  10
```

如果网络只验证“签名正确”，两笔交易的签名都可能通过。

真正的问题变成：

> **对于同一份状态，网络应该接受哪一个状态转换？**

如果不同节点接受了不同交易，账本就会分叉，最终状态无法统一。这就是**双重花费（Double Spending）**问题。

因此，去中心化账本不仅要验证单笔交易的授权，还必须解决：

- 交易之间是否存在冲突
- 冲突时以什么顺序为准
- 最终所有诚实节点应保存什么样的状态

没有统一的交易顺序和冲突裁决机制，账本就会崩溃。

---

## 2.4 Transaction：状态转换请求

一个非常实用的工程视角是：

> **Transaction 是向区块链提交的一份状态转换请求。**

它不是“钱本身”，而是“请求把旧状态变成新状态”的指令。

可以抽象成：

```text
Old State
    │
    │ Transaction
    ▼
Validation / Authorization
    │
    ▼
Execution
    │
    ▼
New State
```

这个视角对后续理解所有主流区块链都至关重要：

- 在 Bitcoin 中，Transaction 主要描述 UTXO 的消费与生成。
- 在 Ethereum 中，Transaction 可以调用智能合约并修改账户状态。
- 在 Solana 中，Transaction 会包含一个或多个 Instruction，明确声明要访问的 Accounts 以及要调用的 Program。

无论具体形态如何变化，Transaction 的本质都是：**一份可验证的、请求状态发生变化的数据。**

---

## 2.5 Block：把交易组织成可验证的历史

网络持续收到大量交易。如果只是零散地保存它们，很难形成“大家共同认可的历史”。

**Block（区块）**可以先理解为：

> 一组按照协议规则组织起来的交易及其相关元数据。

多个区块按照规则链接起来，形成历史：

```text
Block 100
   ↓
Block 101
   ↓
Block 102
   ↓
Block 103
```

这就是“Blockchain（区块链）”这个名字最直观的来源。

区块的作用至少包括：

- 把交易批量组织起来
- 为交易提供一个明确的位置（在哪个区块、什么高度）
- 通过链接关系形成可追溯的历史结构

---

## 2.6 Hash：为什么修改历史会变得困难？

**Hash（哈希）**是一种数据摘要函数。你可以先把它想象成：

```text
任意长度的数据
      ↓
Hash Function
      ↓
固定长度的“指纹”
```

重要性质：

- 输入哪怕发生极小变化，输出通常会剧烈改变（雪崩效应）。
- 从输出反推输入在计算上极其困难。
- 相同输入必然产生相同输出。

区块通常会引用前一个区块的哈希：

```text
Block 100
  hash = H100
      ↓
Block 101
  prev_hash = H100
  hash = H101
      ↓
Block 102
  prev_hash = H101
```

如果攻击者修改了 Block 100 的内容，`H100` 就会改变，导致 Block 101 的 `prev_hash` 不再匹配，后续所有区块的链接关系都会被破坏。

因此，哈希提供的是一种**完整性结构**：它让“悄悄修改历史”变得容易被发现。

需要强调的是：

> 哈希本身并不“神奇地禁止修改”。真正的安全性还来自共识机制、节点验证、经济成本等因素。哈希只是让篡改变得可检测，并大幅提高重写历史的成本。

---

## 2.7 Consensus：谁决定最终历史？

现在问题来了。网络是分布式的，消息传播需要时间，不同节点可能看到不同的交易顺序，甚至暂时接受不同的区块：

```text
节点 A 先看到：Tx A，然后看到 Block X
节点 B 先看到：Tx B，然后看到 Block Y
```

如果没有统一规则，网络就会分裂成多个互相矛盾的历史。

**Consensus（共识）**要解决的核心问题是：

> **网络最终接受什么历史、什么状态？**

它不是简单的“大家举手投票”，也不是“所有机器同时执行同一段代码”。不同区块链的共识机制可以差异很大（Proof of Work、Proof of Stake 等），但目标一致：让诚实参与者最终对有效历史达成共同认识。

可以把共识理解成分布式系统中的“最终真相裁决机制”。

---

## 2.8 一个完整的共同记账流程（直觉版）

把前面的机制串起来，可以得到一个简化的流程：

```text
用户用私钥签名
      ↓
生成 Transaction（状态转换请求）
      ↓
广播到网络
      ↓
节点验证签名 + 规则（余额、冲突等）
      ↓
交易进入待处理集合
      ↓
被打包进 Block
      ↓
通过 Consensus 被网络接受
      ↓
成为共同历史的一部分
      ↓
状态更新为 New State
```

每一层都在解决前面提到的某个具体问题：授权、防双重花费、表达变更、组织历史、形成共同认识。

---

## 本章小结

区块链共同记账并不是单一技术，而是一组机制协同工作：

| 机制 | 主要解决的问题 |
|------|----------------|
| Digital Signature | 授权：证明操作确实由控制者发起 |
| Validation | 合法性：余额、规则、冲突等是否满足 |
| Transaction | 表达：状态转换请求的载体 |
| Block | 组织：把交易变成可链接的历史单元 |
| Hash | 完整性：让篡改历史变得可检测且成本高 |
| Consensus | 共同认识：网络最终接受什么历史和状态 |

这六个概念构成了理解后续 Bitcoin、Ethereum、Solana 的共同基础。它们的差异，很大程度上就体现在“状态如何表达、交易如何授权与验证、执行如何进行、共识如何达成”这些细节上。

## 本章术语

| 术语 | 含义 |
|------|------|
| Digital Signature | 数字签名，用私钥签名、公钥验证的授权机制 |
| Private Key / Public Key | 私钥（保密）与公钥（公开） |
| Double Spending | 双重花费，同一份价值被重复使用 |
| Transaction | 交易，请求状态发生变化的操作 |
| Block | 区块，按协议组织起来的一组交易及元数据 |
| Hash | 哈希，数据的固定长度摘要（指纹） |
| Consensus | 共识，网络就有效历史与状态达成共同认识的机制 |
| Validation | 验证，检查交易是否符合协议规则 |
